# vLLM运维文档嵌入RAG的方法

针对《告警驱动的推理平台运维Runbook》这份 Runbook 的结构特点（章节多、表格多、命令块多、案例条目化），在 Dify 1.17.1 中建知识库时的关键配置如下，按配置界面顺序给出。

## 一、Dify嵌入设置

### 1.1 Embedding 模型与向量维度

- 知识库使用经 LiteLLM 接入的 `qwen3-embedding`（Text Embedding 类型，上下文 32768）。
- **向量维度必须与实际输出一致**（Qwen3-Embedding-4B 默认 2560 维）：先在 Dify 模型供应商处保存该模型并用一条文本试嵌入成功，再建库。维度填错会导致入库直接报错。
- **同一个知识库生命周期内不要更换 Embedding 模型**。本 Runbook 入库后若换模型，向量空间不兼容，必须整库重建索引。

### 1.2 分段设置（Chunking）

推荐**父子分段模式**（Dify 1.x 的"父子检索"）：

| 配置项       | 推荐值                                                       | 理由                                                         |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 分段模式     | 父子分段                                                     | 子块做向量召回（精准匹配告警名、报错原文），父块返回完整上下文（一条完整的处置流程），避免"召回到鉴别命令但丢了处置动作" |
| 父块分隔符   | `\n## ` 或按 `###` 二级/三级标题                             | 本文档按 `### 5.x` 组织告警条目，按标题切可保证每条告警 Runbook 是一个完整父块 |
| 父块最大长度 | 2048–4096 tokens                                             | 一条告警条目（含义+根因+命令+处置）约 800–2000 tokens，留足余量 |
| 子块最大长度 | 300–500 tokens                                               | 子块承载检索匹配，小颗粒度提升告警名/错误码命中率            |
| 分段重叠     | 50–100 tokens                                                | 防止根因列表与处置步骤被切断                                 |
| 预处理规则   | 勾选"替换连续空格/换行"；**不要**删除 URL 和邮箱（文档中的 FQDN、端口是检索关键词） |                                                              |

两个特别注意点：

1. **表格的处理**：§3 告警矩阵是 Agent 的核心字典，但长表格被切断后单行会失去表头语义。建议导入前把 §3 矩阵转为每行一条独立短文本（如"告警 VLLMHighKVCacheUsage，层级 vllm，严重度 warning，含义…，根因…，Runbook 5.4"），或在自定义模式下把该表单独设为一个完整分段。
2. **代码块完整性**：curl 命令和启动命令必须整段保留，不能被切碎——父子分段 + 按标题切分天然满足，若用通用模式需把分段长度调大到能容纳最长的命令块（§6.2 约 400 tokens）。

### 1.3 索引方式

- 选**高质量索引**（向量索引），不要选经济模式（关键词倒排）——单靠关键词无法支撑"描述性故障现象 → 匹配相似案例"的语义召回（如告警描述"KV Cache 使用率 96%"要能命中 §5.4）。

### 1.4 检索设置（Retrieval）

| 配置项     | 推荐值                                                       | 理由                                                         |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 检索方式   | **混合检索**（向量 + 全文/关键词）                           | 运维语料双通道刚需：告警名 `VLLMServiceDown`、Xid 79、报错原文靠关键词精确命中；故障现象描述靠向量语义命中 |
| 权重       | 语义 0.7 / 关键词 0.3 起步                                   | 告警驱动的查询多含精确标识符，关键词权重不宜低于 0.3         |
| Rerank     | 如资源允许，启用 Rerank 模型（可再部一个 Qwen3-Reranker 经 LiteLLM 接入） | 告警条目结构相似（§5.1–§5.12 同构），仅靠向量分数容易混淆相邻条目，Rerank 收益明显 |
| TopK       | 4–6（父子模式指召回的父块数）                                | 一次 RCA 通常需要 1 条告警条目 + 1 条关联案例 + 1 段决策树，4–6 足够且不稀释上下文 |
| Score 阈值 | 0.3–0.5 起步，宁低勿高                                       | RCA 场景漏召回的代价（Agent 臆断根因）远高于多召回；过低再上调 |

### 1.5 元数据打标（决定排障场景的上限）

入库时为文档（或分段）打标，并在 Agent 节点检索时启用元数据过滤：

| 元数据字段  | 取值示例                                      | 用途                                      |
| ----------- | --------------------------------------------- | ----------------------------------------- |
| `layer`     | infra / gpu / vllm / litellm / dify           | 与代码执行节点输出的 `layer` 字段联动过滤 |
| `alertname` | VLLMServiceDown 等（§5 各条目单独成块时标注） | 告警名精确路由                            |
| `doc_type`  | runbook / 案例 / 契约 / 决策树                | 案例库与流程文档可分别加权                |
| `version`   | v2.1                                          | 多版本并存时防旧版污染                    |

落地建议：§5 的 12 个告警条目和 §10 的案例**逐条拆分入库并各自打标**，比整篇导入效果好得多。可用 Dify 的"自定义分段"或预处理脚本完成。

### 1.6 与 Workflow / Agent 节点的联动配置

1. **查询构造**：Agent 节点的知识库检索输入不要直接丢整个 Webhook 原文，用代码执行节点规范化后的 `alert_name + summary + description + layer` 拼接为查询串——与文档中告警名、术语严格对齐，命中率最高。
2. **prompt 中声明引用义务**：要求 Agent 输出 `evidence` 字段时必须引用召回片段（对应 Runbook §2.3 的契约），这同时是你评估 RAG 召回质量的手段。
3. **`runbook_hint` 直达**：§3 矩阵登记了章节号，可在 Workflow 里把 `runbook_hint`（如 "5.4"）拼进查询串（"VLLMHighKVCacheUsage 5.4"），利用关键词通道直接锚定目标条目，相当于一层"软路由"。

### 1.7 运维性配置

- **文档更新即重建**：Runbook 每次修订（v2.1 → v2.2）后，在知识库中替换文档并重新向量化；`version` 元数据同步更新。
- **召回质量回归测试**：固化 10–20 条测试查询（每条对应一个历史告警描述），每次调整分段/检索参数后跑一遍，记录命中条目是否正确——这是调参的客观依据，避免凭感觉改配置。

**总结**：父子分段按告警条目切、混合检索保双通道、元数据联动 `layer`/`alertname` 过滤、案例库单独打标——这四项做对了，这份 Runbook 的 RCA 命中率就有保障；其余参数（TopK、Score 阈值）用回归测试集迭代收敛即可。

## 二、召回测试

测试分三层：**知识库内召回测试 → 模拟告警的端到端测试 → 回归测试集固化**。下面给出方法和具体的验证问题集。

### 2.1 测试入口与方法

#### 2.1.1. 知识库"召回测试"（Hit Testing）

Dify 知识库页面 → 左侧"召回测试"，输入查询文本，直接查看：
- 命中了哪些**父块**（应完整呈现一条 §5.x 告警条目）；
- 是哪些**子块**触发的召回、各自得分；
- 混合检索下向量通道和关键词通道各自的贡献。

每输入一条查询，记录三项判定：**目标条目是否命中（TopK 内）、排名是否第一、父块内容是否完整**。这是调参（分隔符、权重、Score 阈值、TopK）的主战场。

#### 2.1.2. 元数据过滤验证

如果入库时打了 `layer` / `alertname` 标签，在召回测试中开启元数据过滤，验证过滤条件是否生效、是否误杀（过滤后该命中的条目必须仍在）。

#### 2.1.3. Workflow 端到端测试

在 Workflow 编辑页用"单步运行/试运行"，构造 AlertManager Webhook 模拟载荷（可直接用 Runbook §2.1 的 JSON 改 `alertname`），跑通"Webhook → 代码执行规范化 → Agent 检索 → 输出根因 JSON"全链路，检查：
- 规范化字段是否符合 §2.2 schema；
- Agent 输出的 `evidence` 是否真实引用了知识库片段（防止幻觉兜底）；
- `confidence` 与 `escalation` 是否符合预期。

### 2.3 判定标准与迭代闭环

1. **通过线建议**：A 组 100% 命中（精确路由是底线）；B 组命中率 ≥ 80%；C 组答案关键事实（命令、端口、参数名）零错误；D 组命中至少 2 个目标章节；E 组零幻觉。
2. **失败模式对应的调参动作**：
   - 告警名查不到 → 检查子块是否切碎了条目标题（回到分隔符配置）；
   - 现象描述命中错误条目 → 调低关键词权重至 0.2 或启用 Rerank；
   - 召回了但父块缺处置步骤 → 确认父块分隔符已改为 `\n### `；
   - 该拒答的没拒答 → 上调 Score 阈值（0.4 → 0.5）或在 Agent 提示词中强化证据引用要求。
3. **固化为回归集**：把 A–E 共 15 条查询连同预期命中记录成表格，每次更新 Runbook 版本（v2.1 → v2.2）、调整分段/检索参数、或更换 Embedding 模型后全量重跑，对比命中率变化——这是防止"改一处参数、坏一类查询"的唯一可靠手段。

先跑 A、B 两组即可快速判断当前建库配置是否达标；C–E 组建议在 Workflow 联调阶段执行，因为它们的判定依赖 Agent 输出而不仅是召回结果。
